# i18n — Internationalisation de bout en bout (ar / fr / en)

> **Statut :** opérationnel (2026-07-12) · Locales : `en`, `fr`, `ar`
> **Règle unique côté client :** envoyer `Accept-Language: ar|fr|en` sur chaque requête.

---

## 1. Les 3 couches du moteur

| Couche | Mécanisme | Couvre |
|---|---|---|
| **Négociation** | Middleware global `SetLocale` (parse q-values, `fr-FR,fr;q=0.9` → `fr`, fallback `app.locale`) | Toutes les requêtes API |
| **Messages système** | `resources/lang/{locale}/messages.php` (guards Finance/RBAC…) + `resources/lang/{ar,fr,en}.json` (littéraux, 1454 entrées ar) + messages de validation Laravel | Erreurs 422/404, toasts |
| **Data dynamique** | `product_translations` (produits) · `translate_utilities` (brands/categories/units) · **`lookup_translations` (générique — tous les dictionnaires)** | Noms/libellés métier |

## 2. Le moteur générique `lookup_translations` (nouveau)

Table polymorphe : `(translatable_type, translatable_id, locale, field, value)`.
N'importe quel modèle-dictionnaire devient traduisible avec le trait :

```php
class VisitMotif extends Model {
    use \App\Traits\HasTranslatedLabel;
}

$motif->translated('name');   // locale active, fallback auto sur la colonne de base
Model::with('lookupTranslations')->get();  // zéro N+1 dans les listes
```

**10 dictionnaires branchés** (trait + morph map + whitelist admin) :

| Module | Entités (slug API) | Champs |
|---|---|---|
| Ventes & SFA | `order-cancellation-reasons`, `direct-sale-reasons`, `visit-motifs`, `payment-terms` | label / name / name+description |
| Géo & Logistique | `geo-area-types`, `itinerary-types`, `loading-reason-codes` | name / name+description / label |
| Workflows | `workflow-definitions`, `workflow-steps`, `workflow-task-templates` | name(+description) |

**Ajouter un 11e dictionnaire** = trait sur le modèle + 1 alias morph map (AppServiceProvider) + 1 ligne dans la whitelist `TranslationAdminController::ENTITIES`.

## 3. API admin de saisie (écran « Traductions »)

Permission : `manage-master-data`.

```
GET /api/backend/translations/entities
→ { entities: [{ entity, translatable_fields, rows_count, translated_rows_count }], supported_locales }

GET /api/backend/translations/{entity}?per_page=50
→ lignes paginées : { id, code, base: {label: "Appel téléphonique"}, translations: { ar: {label:"مكالمة هاتفية"} } }

PUT /api/backend/translations/{entity}/{id}
Body: { "translations": { "ar": { "label": "مكالمة هاتفية" }, "en": { "label": "Phone call" } } }
→ chaîne vide = supprime la traduction (retour au fallback)
```

**UI suggérée :** sidebar = `entities` (avec badge `translated_rows/rows`), table = colonne de base + une colonne par locale, sauvegarde par ligne.

## 4. Points de consommation déjà câblés

| Endpoint terrain | Traduction |
|---|---|
| `GET /salesperson/catalog/products` | `name` produit via `product_translations` + recherche multilingue |
| `GET /salesperson/orders/cancellation-reasons` | labels via `lookup_translations` — **cache par locale** |
| `GET /salesperson/orders/direct-sale-reasons` | idem |
| `GET /salesperson/catalog/loading-reasons` | idem |
| Options payment terms (dropdown BC) | `name` traduit (`PartnerSelectablePaymentTermsService`) |

> ⚠️ **Caches par locale** : tout endpoint qui cache un dictionnaire DOIT inclure
> `app()->getLocale()` dans sa clé (sinon un vendeur ar reçoit le cache fr).
> Les caches des 3 pickers ci-dessus sont invalidés automatiquement au PUT admin.

## 5. Ce qui reste à câbler (le trait rend ça mécanique)

Les listes admin qui renvoient `geo_area_types`, `itinerary_types`, `workflow_*` affichent
encore la colonne de base. Pour les localiser : `->with('lookupTranslations')` +
`$row->translated('name')` dans le payload — même pattern qu'au §4.

## 6. Déploiement

```bash
php artisan migrate            # crée lookup_translations
```
Aucun seed requis — fallback silencieux sur les colonnes de base tant que les
traductions ne sont pas saisies dans l'écran admin.
